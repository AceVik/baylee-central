# Initial threat model

This is a review input, not a completed security assessment. Assets: passwords,
master/device/content keys, identity and signing keys, account metadata, encrypted
backups, private decks/replays, roles, training data, software updates and audit logs.

Attackers include unauthenticated clients, malicious account owners, hostile or
compromised gateways, stolen devices/sessions, malicious uploads, compromised
operators/storage, dependency attackers and abusive directory registrants.
Trust official client distribution separately from foreign gateways. Central
compromise must not expose existing vault plaintext, but can expose metadata,
deny service and attack authentication; weak-password guessing remains a risk
(online it is slowed, not ended: the row below).

| Threat | Required control | Evidence before release |
| --- | --- | --- |
| Cross-account access/IDOR | Ownership on every metadata/object operation | Negative tests across accounts, devices and gateways |
| Credential replay/downgrade | Bound protocol transcripts, one-use challenges, migration state | RFC vectors and adversarial replay/destination tests |
| Token theft/confusion | Issuer, audience, algorithm and action validation; rotation | Wrong issuer/audience, expired/revoked token tests |
| Admin escalation | Separate owner/heartbeat keys, scoped roles, step-up; Central administrators act through the runtime login, guarded by the browser-only `Admin` request, the role checked where it acts, a password sign-in under 30 minutes for changes, the append-only audit and the exact grant check ([administration](administration.md)); a taken-over service can appoint administrators and act without an audit event | Compromised heartbeat cannot mutate admins; refused stale, self and last-administrator changes; concurrent removals leave one |
| Kept browser chat identity | The chat identity sealed in IndexedDB under a non-extractable AES-256-GCM key, bound by AAD to account, epoch and tag, written only by the chat's Worker, one record per browser, forgotten on sign-out, at the session's end (also detected at the next page start), on Central's refusal and with another account's chat ([chat](central-chat.md)); script in the origin or the profile's owner can take it while it exists | Owner, foreign epoch/tag, altered ciphertext/IV and non-exportable key tests; e2e: kept after sign-in, opened after a reload without a password, empty after sign-out |
| Vault substitution/rollback | AEAD context, epochs, revisions, explicit freshness limits | Swapped objects/accounts, stale revisions, fresh-device tests |
| Password reset takeover | Separate authentication reset and key recovery | Email/session possession cannot decrypt or pair devices |
| Account deletion by a session thief | A fresh OPAQUE proof of the password inside the deletion, bound to its session and listener, charged to the login budget; administrators and open moves refused, rechecked under the account's lock ([account deletion](account-deletion.md)); a taken-over service can delete accounts | Stolen-session, crossed, replaced and lost-answer tests; an appointment racing the deletion; no row naming the account left |
| Export over-disclosure | The session's own account only, a sign-in under 30 minutes, no credential, wrapper, digest or ciphertext, bounded lists | Stale, other-kind and foreign-session tests; field-by-field comparison |
| Data loss in migration | Durable state machine, preserved sources, restore proof | Failure injection at every transition |
| Online password guessing, credential stuffing and password spraying; sign-in used to keep someone out | Every sign-in start is a guess until its proof (KE2 lets a guess be checked offline), a change's start two, a deletion's one, counted in memory per account (8 a minute, 30 an hour, 100 a day from places that are not its own), per account at an address (10 an hour, 30 a day), per address over all accounts (30 an hour, 100 a day; an IPv6 /64, and four times that for its /48) and for all made-up ids together as one account; a proof gives the guess back and makes the address the account's own for 30 days, where only its own count applies, until another password is set or the account is deleted; per-address budgets on both listeners for discovery, sign-in starts, the legacy sign-in and reset starts, and 600 requests a minute without a session; bounded tables that forget their oldest and refuse nobody; refusals are the existing `Busy` and spend nothing ([native login](native-login.md#guessing-a-password-online)). What stays: 100 guesses a day at one account from many addresses (36,500 a year) and 30 more a day from whoever shares one of its own addresses, so a common password still falls, and the page's only rule is eight characters; 100 requests a day from four addresses keep an account's password sign-in closed at every address that is not its own, 10 an hour by someone at its own address there too, and after a restart no address is anyone's own; whoever sends from an address can find out whether a given account signed in from it in the last 30 days (a household, an office, a carrier's shared address, a VPN's exit); a shared address (a campus, a carrier) that spends its count shuts out its newcomers; the counts live in one process's memory; a client without a proxy's forwarded address is counted per account only; no proof of work and no device token for sign-in, which need a new client | Unit tests with a clock of their own for every count and bound (one address at many accounts, many addresses at one account, /64s of one /48, made-up ids, full tables, refunds, refusals that spend nothing, an own place's end, another password forgetting the old one's places); the address the listeners count by, forged hops included; real HTTP and PostgreSQL: seven guesses then `Busy` from every other address and natively, the holder served at home meanwhile, eleven right sign-ins in a row, a made-up id answered like an account's and counted, and on the account listener with a proxy's hop the holder's address served while a guesser's is refused, 30 discoveries a minute and then `Busy` for that address alone, a forged earlier hop included |
| Legacy password guessing and verifier theft | Central's one password path, until the store's deadline ([native login](native-login.md#legacy-login)): its own schema and role, the runtime role closed out and both checked at startup; Argon2id under the gateway's fixed parameters only, wiped work memory, constant-time comparison; one answer and the same work for every refusal before the proof; 30 sign-ins a minute in all and five per name, ten failures lock an account for an hour; rows deleted at the close and after the deadline. A taken-over service or a copy of the store can attack these few verifiers offline, as one of the gateway's database could; the lockout lets anyone who knows a legacy name lock it out for an hour at a time | Wrong password, budget, lockout, replayed ticket, closed move, Central-only name and bridge-refusal tests over real HTTP; role-privilege tests both ways; the gateway's own hash reproduced |
| Registration abuse and name probing | Open since 11.11.2026 ([registration abuse](registration-abuse.md), reviewed as an attacker the same day, §"Hardened"): Central's own proof of work, by the owner's decision of the same day one that costs memory (§"A proof that costs memory": Argon2id through the vetted crate, 16 MiB and one pass for each evaluation, eight parts, 4 bits per part, one Rust function for the page's Worker and for Central, held together by a pinned vector; random nonce held in memory with the price it was issued with, one use, three seconds at the soonest), checked and spent before the name is looked at, by one of the service's four workers and off the executor (`Busy` without a worker, and the challenge is kept); no SHA-256 challenge is handed out or taken; up to six bits more with the hour's registrations, up to four for a request that looks automated (missing browser headers, a tool's user agent, a driven browser the page reports, an address or its block asking often), six together at most, never a refusal; a challenge lives five to twenty minutes, and the table (40,000) cannot be crowded out within the shared budget; `Register` 5 an hour and 10 a day per address, both challenge requests 20 an hour together; a honeypot and a minimum fill time on the page; an administrator's audited switch closes registration. What stays: native code evaluates the proof about 1.3 times as fast as the page's WebAssembly, one core against one (measured; SHA-256 was thirteen times), a script uses every core where the page uses one, and tuned or graphics hardware was not measured, so a registration costs a script about what it costs a person's processor and the proof does not stop one who has many machines and many addresses in many blocks; Central now computes for every `Register` that names a living challenge (one evaluation for a wrong answer, eight for a right one, four checks and 64 MiB at once at the most), within the address's 5 an hour and the budget all callers share; addresses that ask at their full budgets make their block's other people pay up to three bits more for the hour, never a refusal; the headers and the page's report are whatever the sender says; whoever solves a proof learns whether one private sign-in name is free; the budget all callers without a session share (32 a second) can be used up from few addresses, which keeps everyone from signing in and registering while it lasts (open, its own review) | Over the real listener and PostgreSQL: a proof used twice, raced (one account of three), solved for less than asked, made up; refusals that tell nothing of the name; no account without a spent proof on either listener; the price by look, by an address's haste and by its block; the newer challenge request weighed and both budgeted alike; the older request and an older solution lead to no account. The pinned vector natively, through the Worker's function and in Chromium with the committed module. Unit: once/too soon/expired, the difficulty stored with the nonce, the rise to six and its fall, the ceiling for every combination, lifetimes, the table at the shared budget's full rate, the header facts and user-agent markers, wire shapes, a busy service keeps the challenge, the test knob only lowers; closed registration refused before the name; switch only for a fresh administrator, audited |
| Resource exhaustion | Bounded KDF, input size/depth, concurrency and storage. Bodies that are announced and withheld: the browser listener gives an address four requests in flight, the account listener four places per address and a quarter of its connections in all to bodies that are late or larger than 64 KiB, so requests whose small body is there are still served ([operations](operations.md#the-account-listeners-connections)). Many addresses can still fill those places for late and large bodies, and a flood of whole requests is left to the proxy. The store's pool has four connections: no operation asks the pool for a second one while it holds a transaction (an administrator's change did until 11.11.2026, so any signed-in browser session could hold all four for the pool's three seconds, again and again; [administration](administration.md)). A session's requests are counted against its bearer's own budget before the budget all sessions share, so one session cannot spend the others', and a bearer is counted as a session's only once an answer has vouched for it, so tokens nobody issued spend neither the sessions' budgets nor the sign-ins' ([native login](native-login.md#a-bearer-nobody-issued)); four vouched-for bearers (two accounts' sessions, or one account's gateway tokens), and seven addresses against the strangers' second, are open ([operations](operations.md#known-limits-of-this-deployment)); an approved gateway's reports have no bound on the bytes stored, and one such gateway can hold both upload slots, open too ([reports](reports.md), pass 3) | Oversized/malformed inputs, load and cancellation tests; withheld bodies over real sockets against both listeners, another address served meanwhile, places given back on every ending; on PostgreSQL, eight changes at once by a session without the role, each refused and none unavailable, another session's read served meanwhile, and eight by an administrator, each done or refused; one bearer asking for a whole shared window is served its own budget and three others theirs beside it; on PostgreSQL, 900 made-up bearers in one instant beside a session's four requests, which are served, on the running service and on a second one that has just started; no request that vouches for a bearer answers a made-up one; four replaced sessions leave the live one its second |
| SSRF through registry | Restricted probes and DNS/IP/redirect checks | IPv4/IPv6, rebinding and redirect attacks |
| A gateway lying about its activity | The four counts of a pulse are the gateway's own claim, and Central cannot check them ([gateway registry](gateway-registry.md#activity-and-the-public-figures)). Each is bounded (100 000, in the wire check, the store and a CHECK), so a claim cannot show an absurd number, and the players in a game are never more than the players connected (the same three places), so a claim cannot contradict itself; they are published only for a gateway an administrator approved and has not disabled, beside that gateway's id, and for 90 seconds after its report; disabling hides them at once. The pulse needs the heartbeat's credential (never a page's cookie, a session, the redemption credential or an `sso`-only token) and is the heartbeat's one statement, so it changes nothing a heartbeat could not and no other gateway's row. Not prevented: an approved gateway can claim any number up to the bound, with any share of its players in a game, and so stand first where the website sorts by players, or inflate a total the website adds up; the website must show the counts as the gateways' own, and the remedy is an administrator's | Over-bound, wrong-credential and rate-limited pulses in the store and over HTTP; more players in a game than connected on the wire, in the store, over HTTP and written to the table past the store; a pulse of the three counts from before the fourth refused by the decoder and over HTTP; pending, disabled and other-row pulses in the store; no pulse on the browser listener; the old heartbeat and directory shapes refusing an activity |
| What the public figures give away | `PublicFigures` is public by design and holds counts only: the number of enrolled accounts and, per reporting gateway, four numbers. No name, origin, address or per-player datum is stored for it or returned, nothing is logged, and one row per gateway is overwritten (no history at Central). The account count is exact and counted at most once a minute, so anyone can watch Central grow, and can see that some registration finished within a given minute, which says nothing about whose (whether a given name exists is `Discover`'s answer already). A reporting gateway's operator publishes how busy the gateway is, minute by minute, to anyone who records it; on a gateway with one or two players that is close to saying when those people are connected and, with the players in a game counted apart, when they play. Reporting is therefore off unless the operator turns it on, and a plain heartbeat withdraws the counts. Requests spend the directory's budgets on both listeners, and the count is one cached number, so asking often costs one page of the gateway table and never a scan of the accounts | Field-by-field shapes of the answers; the count against the table with unfinished and deleted accounts; budgets shared with the directory on both listeners |
| Upload parser compromise | Isolated bounded validation, no arbitrary execution | Fuzzers, decompression bombs, invalid replay versions |
| Website compromise | CSP/CSRF/output encoding, isolated credentials | XSS/CSRF/session fixation and origin tests |
| The website's count of page views | Off unless a deployment names a file (`views`); then the website's server keeps one number for all pages and all visitors and the day it began, nothing about a request (no address, cookie, identifier or page), in the one file it may write, replaced whole by a rename and refused at start if it is not this server's own. The number is a claim about requests, not people: whoever sends requests that look like a browser's navigation raises it, up to the rate the server answers at, and it stops at its type's end instead of wrapping. It reaches the pages once a minute, so no visitor sees their own visit move it and a page's entity tag does not change per request. The file's directory must be the service's own: a directory others can write lets them point the file elsewhere ([operations](operations.md)) | `views.rs` unit tests (what counts, malformed and oversized files, the write), `pages.rs` (a visit counts once and never changes its own answer; a bad file stops the start; the privacy notice names the count only where it is kept) |
| Training re-identification | Data minimization, separated metadata, risk assessment | Stream/public replay linkage attempts and log review |
| Poisoning/model cheating | Provenance, quarantine, engine validation, visibility masks | Forged transitions and hidden-information leakage tests |
| Supply-chain compromise | Pinned dependencies/actions, SBOM, review and signing | Reproducible provenance and update verification |
| Insider/backups compromise | Least privilege, key separation, encrypted backups | Restore drills, access audit and key rotation drill |

Specify rate limits without making shared IP addresses a trivial account lockout
weapon. Audit sensitive actions without recording secrets or complete payloads.
Define which metadata remains visible and retain only what serves an explicit purpose.
Account enumeration, device substitution, session fixation and recovery-code brute
force must be explicitly covered in M2 tests. Hardware compromise and malicious
client binaries cannot be solved by server-side encryption design.
