# Advent release, entitlement and presentation checks

The fixtures exercise both the native HTTP service and the deployed PostgreSQL runtime role. Their campaigns contain 24 generated tactical boards, generic marker strings and synthetic byte patterns. The test calendar has a different year from the published event. No production day-to-reward mapping or prize image is required.

| Boundary | How the fixture checks it |
| --- | --- |
| Release clock | The restricted importer establishes Europe/Berlin midnight for December 1, December 24 and exclusive January 7. The store test verifies the UTC instants in PostgreSQL. The fixture operator then moves only that synthetic campaign's interval across the real server clock. Closed, first-open, final-open, last-day catch-up and expired responses all traverse the normal API. The default-calendar lookup uses the nearest upcoming or active campaign and clears after the last campaign closes. |
| Unopened material | The native response before launch contains the schedule and door states. It has no puzzle, item ID, title, tier, art metadata or digest. Tests request future puzzles, hints and claims by day, and try a known future asset ID and its exact digest against the art path. Even a matching cache key requires authority to read the image. The calendar mosaic has its own event-window check. |
| Solves and claims | A legal losing line earns nothing. Three different successful moves satisfy the synthetic board's goal. Successful submission records the per-door solution and permanent inventory grant in one transaction. A fixture constraint interrupts entitlement insertion and the solution rolls back. Repeated and concurrent submissions and collection reads preserve the original acquisition. Two participants can independently earn the same cosmetic. |
| Catch-up and persistence | A player can skip doors and solve the finale on January 6. The final reward is already in the inventory after the solve and can first be viewed after the event. A later campaign offering the same cosmetic requires a fresh solution to its door and preserves the original inventory item. Closed, unsolved doors refuse new submissions and claims. Existing owned images stay available through a new authenticated read after closing. |
| Native media | Authorization precedes cache validation. The SDK reassembles two full 192-KiB pages and a seven-byte tail, and verifies the complete content. The tests compare all bytes, a cache hit, an unauthorized hit, a misaligned offset and a request beyond the end. A direct uncredentialed HTTP GET using the fixture digest produces no asset. |
| Ranked appearance | Central accepts choices for the calling live participant's own seat, validates ownership and slot type, and freezes that selection. Peers see only the selected slots. An observer cannot resolve metadata or cached bytes. Finishing the match retires the presentation while both owners keep their inventory. |
| Casual appearance | A native gateway login and explicit proof bind the gateway, game, chair and wearer. The host's own credential and the wearer's admission SID must agree. Cross-host, wrong-seat and wrong-SID cases fail. An accepted proof can expose only its selected slots. A retry respects the original deadline. Expiry also closes the cache path. After a real new native login, both a fresh consent proof and the new admission SID are required. Only the previously confirmed chair selection is recovered. A different operator cannot close it, and the original operator can retire it idempotently when the game ends. |

The calendar intentionally discloses the release schedule. Previously authorized players or operators can retain and share content they actually received. The protocol controls future releases and access to Central's stored bytes. It cannot retract copies already delivered to an authorized device. The synthetic Store and SDK tests exercise release and transport semantics. Image-format validation and the private pack have separate provisioning checks.
